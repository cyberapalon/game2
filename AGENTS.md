# Работа Codex над «Глубиной»

## Начало задачи и границы

- Прочитай `PRD.md`, `docs/toolchain.md` и инструкции для затронутого каталога.
  Продуктовая цель — оригинальное браузерное 2D action-platformer демо на 10–15 минут.
  MVP ограничен прологом и «Корнями»; новые биомы, procedural generation,
  мультиплеер и системы вне PRD не добавляй без задачи.
- Текущий baseline — существующий Godot-проект: `project.godot`, поверхность,
  контроллер, HUD, GdUnit4 6.2.2, Web E2E и три export presets. Развивай
  существующие сцены в рамках запрошенной фазы; не создавай проект заново.
- Согласованный стиль — «Пепел и фарфор», концепт 1. Читай
  `docs/art-direction.md` и `ASSET_PROVENANCE.md` перед изменением графики.
  Персонажи, окружение и эффекты используют полноценные AI-PNG; не подменяй
  рисованный арт программными SVG. `tools/build_art_resources.py` только
  извлекает ресурсы из сохранённых исходников. Старый SVG-генератор — архивный.
- В Cloud используй существующий checkout; отдельный worktree обычно не нужен.
  Проверь `git status`, сохрани чужие изменения. Scratch-файлы — в `work/`.
- В каждом новом shell выполни `source /workspace/.godot-cloud/env.sh` и
  проверь `godot --version`: требуется `4.6.3.stable.official.7d41c59c4`.
  Не считай процессы или переменные предыдущей задачи сохранёнными.
- Если нет PRD, нужного доступа или проверяемого инструмента и это блокирует
  задачу, останови зависимую работу и задай конкретный вопрос. Не подменяй
  неизвестное успешной проверкой. Необязательный MCP не блокирует CLI-workflow.

## Небольшие итерации

1. Сформулируй одно наблюдаемое изменение и критерий готовности из PRD.
2. Выбери минимальный затронутый набор сцен, скриптов и ресурсов; не совмещай
   новую механику с посторонним рефакторингом или обновлением зависимостей.
3. Внеси небольшой законченный шаг и сразу запусти целевые проверки.
   Для исправления поведения сначала воспроизведи ошибку и добавь уместный
   регрессионный тест. Для документации достаточно структурных проверок.
4. После целевых проверок продолжай следующий шаг. Полный набор проверок
   выполняй перед завершением задачи и PR, а не после каждой правки.
5. В отчёте укажи результат, команды, ограничения и непроверенное поведение.

## Архитектура Godot

- Предпочитай композицию небольших сцен глубокой иерархии наследования.
  Сцена владеет своими узлами и предоставляет небольшой явный интерфейс.
  Родитель координирует дочерние узлы; события передавай типизированными
  сигналами. Не ищи соседей через длинные `get_parent().get_node(...)` цепочки.
- Группируй `.tscn`, `.gd` и локальные ресурсы по функции: например,
  `game/player/`, `game/enemies/`, `world/rooms/`, `ui/`. Общие ресурсы — в
  `shared/`, тесты — в `tests/`. Создавай каталоги по необходимости.
- Конфигурацию и баланс храни в типизированных `Resource`/`.tres`, поведение —
  в сценах и скриптах. Не меняй общий Resource отдельно для каждого экземпляра
  без осознанного копирования или `resource_local_to_scene`.
- Autoload допустим для обоснованного общего жизненного цикла (например,
  сессии или сохранения), но не вместо передачи зависимостей. Не создавай
  глобальный event bus или абстрактный framework заранее.
- Комнаты — вручную созданная сеть с явными входами/выходами. Прогресс босса,
  получение способности и глубина должны иметь проверяемые контракты;
  UI отображает состояние, а не владеет правилами прогресса.
- Движение и столкновения — фиксированный `_physics_process`; презентация
  отделена от авторитетного игрового состояния. Используй API Godot 4.6,
  в том числе `CharacterBody2D` и `TileMapLayer`, когда они подходят задаче.

## GDScript и ресурсы

- GDScript, standard Godot без .NET. Типизируй параметры, возвращаемые значения,
  сигналы и коллекции там, где тип известен. `Variant` оставляй для реальных
  динамических границ с проверкой данных.
- Следуй [стилю Godot 4.6](https://docs.godotengine.org/en/4.6/tutorials/scripting/gdscript/gdscript_styleguide.html):
  UTF-8/LF, табы в `.gd`, `snake_case` для файлов/методов/переменных,
  `PascalCase` для классов/узлов, `CONSTANT_CASE` для констант.
- Кешируй стабильные ссылки на узлы через `@onready`, передавай зависимости
  через `@export` или явную инициализацию. Не обращайся к дочерним узлам из
  `_init()`. Не используй `@onready` и `@export` на одной переменной.
- Учитывай удаление узлов после `await`, освобождай созданные тестом объекты,
  избегай повторных подключений сигналов. Не скрывай новые parser/runtime
  errors и не подавляй предупреждения без объяснения причины.
- Сохраняй `.uid`, исходные ассеты и импортные настройки `*.import`, когда
  они появились. Не коммить `.godot/`, кэши, сборки, отчёты и секреты.
  Пути ресурсов должны работать на Linux с учётом регистра.

## Навыки без дублирования

Codex обнаруживает `.agents/skills/*/SKILL.md`. Открывай нужный навык по задаче:

| Навык | Когда нужен |
| --- | --- |
| `godot-gdscript` | GDScript, ресурсы, сигналы, композиция сцен, разбор ошибок |
| `godot-2d-gameplay` | Контроллер, столкновения, бой, комнаты, прогресс |
| `godot-2d-art-animation` | Импорт 2D-графики, SpriteFrames, анимации, слои |
| `godot-testing` | Выбор тестов, GdUnit4, CLI-экспорт, Web E2E и сборки |

Общие правила живут здесь; команды и границы проверок — в `docs/validation.md`.
Не копируй один workflow в несколько навыков. Проверка обнаружения:
`python3 tools/check_codex_skills.py` (настоящий Codex app-server `skills/list`).

## Проверки и воспроизводимые сборки

- Во время реализации запускай импорт/проверку затронутых скриптов и связанные
  GdUnit4 suites. Изменения ввода, UI или анимации проверяй в Web Chromium.
  Подробные команды и предусловия: `docs/validation.md`.
- Перед завершением: проверка конфигурации, импорт и все собственные `.gd`,
  все логические/scene-тесты, запуск главной сцены, чистый release-экспорт Web,
  браузерные E2E и просмотр diff. Windows/Linux экспортируй, когда их пресеты
  введены в проект или меняется соответствующий pipeline.
- Исторический набор для стадии без проекта: `tools/check_codex_skills.py`,
  проверка Markdown/JSON и `git diff --check`, затем существующий
  `python3 /workspace/.godot-cloud/validate.py`. Это тесты инфраструктуры;
  игровые проверки помечаются «не применимо», а не «прошли».
- Проверяй exit code, engine log и свежий XML/JSON-отчёт: 0 тестов, зависший
  процесс или старый отчёт не означают успех. Кадровый smoke не проверяет механику.
- Закрепляй версии и контрольные суммы из `docs/toolchain-lock.json`.
  Экспортные шаблоны должны точно соответствовать Godot 4.6.3. Не используй
  `latest`, непроверенные community installers или автоматические обновления.
- Для Web выбери Compatibility (`gl_compatibility`), single-thread и без
  GDExtensions. Коммить `project.godot` и `export_presets.cfg` после отдельной
  инициализации; приватные export credentials не коммить.
- Сборка начинается с чистого выходного каталога и импорта из исходников;
  фиксируй commit, версии, команды и SHA-256 артефактов. Воспроизводимость
  workflow не означает обещание побайтово одинаковых бинарников.
- Не устанавливай второй test framework, LSP/formatter, MCP или asset-service
  без доказанной необходимости. MCP-кандидат и условия включения описаны в
  `docs/godot-mcp.md`; текущая конфигурация MCP не активирует.
